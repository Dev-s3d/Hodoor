# دليل تطوير المشروع (Project Guidelines)

يهدف هذا الملف إلى مساعدة المطورين على فهم طريقة تطوير مشروع Hodoor وإضافة مزايا جديدة دون التأثير على هيكل المشروع أو
استقرار النظام.

---

# مقدمة

تم بناء مشروع Hodoor بطريقة منظمة تعتمد على:

* البرمجة الكائنية (OOP)
* فصل المسؤوليات
* إعادة استخدام الكود
* سهولة التوسع

لذلك عند إضافة أي ميزة جديدة يجب الالتزام بنفس الأسلوب المستخدم داخل المشروع.

---

# قبل البدء بالتطوير

قبل إضافة أي ميزة جديدة يجب الإجابة على الأسئلة التالية:

1. هل تحتاج الميزة إلى جدول جديد؟
2. هل تحتاج Class جديد؟
3. هل تحتاج صفحات جديدة؟
4. هل تحتاج صلاحيات جديدة؟
5. هل تحتاج تسجيل عمليات داخل Logs؟
6. هل تحتاج تحديث التوثيق؟

---

# إضافة جدول جديد

إذا كانت الميزة تحتاج تخزين بيانات جديدة.

مثال:

```text
المواد الدراسية
```

يجب إنشاء جدول جديد.

مثال:

```sql
CREATE TABLE subjects
(
    id           INT AUTO_INCREMENT PRIMARY KEY,
    subject_name VARCHAR(100) NOT NULL,
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

---

# إضافة Class جديد

لكل ميزة جديدة يجب إنشاء Class مستقل.

مثال:

```text
classes/clsSubject.php
```

---

## مسؤولية الكلاس

يجب أن يحتوي فقط على منطق إدارة المواد.

مثل:

* إضافة مادة.
* تعديل مادة.
* حذف مادة.
* عرض مادة.

---

## يمنع

إضافة منطق:

* الطلاب.
* الحضور.
* التقارير.

داخل نفس الكلاس.

---

# إضافة Module جديد

بعد إنشاء الجدول والكلاس.

يتم إنشاء مجلد جديد داخل:

```text
modules/
```

مثال:

```text
modules/subjects/
```

---

# الملفات الأساسية لأي Module

يفضل أن يحتوي على:

```text
subjects/
│
├── index.php
├── create.php
├── store.php
├── view.php
├── edit.php
├── update.php
└── delete.php
```

---

# إضافة عنصر في القائمة الجانبية

إذا تمت إضافة Module جديد.

يجب إضافة رابط داخل:

```text
includes/sidebar.php
```

مثال:

```php
<a href="<?= clsPath::subjects(); ?>index.php">
    المواد الدراسية
</a>
```

---

# إضافة مسار جديد داخل clsPath

يفضل إضافة جميع المسارات الجديدة داخل:

```text
classes/clsPath.php
```

مثال:

```php
public static function subjects()
{
    return self::root() . 'modules/subjects/';
}
```

---

# إضافة صلاحية جديدة

إذا كانت الميزة تحتاج صلاحيات خاصة.

يجب تحديث:

```text
users.role
```

أو إنشاء نظام صلاحيات أكثر تفصيلاً مستقبلاً.

---

## مثال

```php
clsHelper::requireRole([
    'admin'
]);
```

---

# إضافة Logs

أي عملية مهمة يجب تسجيلها.

مثال:

```php
clsLog::add(
    $conn,
    'إضافة مادة',
    'تمت إضافة مادة جديدة'
);
```

---

# إضافة Validation

قبل حفظ أي بيانات.

يجب استخدام:

```text
clsValidator
```

مثال:

```php
if (!clsValidator::required($subject_name)) {
    $errors[] = 'اسم المادة مطلوب';
}
```

---

# إضافة رسائل النظام

بعد نجاح أو فشل العملية.

مثال:

```php
clsHelper::sessionSet(
    'success',
    'تمت العملية بنجاح'
);
```

أو:

```php
clsHelper::sessionSet(
    'error',
    'حدث خطأ أثناء التنفيذ'
);
```

---

# دورة إنشاء ميزة جديدة

يفضل اتباع الخطوات التالية:

```text
فكرة جديدة
      ↓
إنشاء جدول
      ↓
إنشاء Class
      ↓
إنشاء Module
      ↓
إضافة Validation
      ↓
إضافة Permissions
      ↓
إضافة Logs
      ↓
اختبار الميزة
      ↓
تحديث Documentation
```

---

# اختبار الميزة

قبل اعتماد أي ميزة جديدة.

يجب التأكد من:

* نجاح الإضافة.
* نجاح التعديل.
* نجاح الحذف.
* نجاح البحث.
* صلاحيات المستخدمين.
* تسجيل Logs.
* سلامة قاعدة البيانات.

---

# تطوير قاعدة البيانات

عند تعديل قاعدة البيانات.

يجب:

1. تحديث ملف SQL الرئيسي.
2. تحديث ملف Database Documentation.
3. اختبار العلاقات.
4. اختبار البيانات الحالية.

---

# تحديث التوثيق

أي ميزة جديدة يجب أن يتم توثيقها.

على الأقل في الملفات التالية:

```text
docs/
```

مثل:

* Database Architecture
* Classes Reference
* Project Guidelines

---

# إضافة مكتبات خارجية

قبل إضافة أي مكتبة جديدة يجب التأكد من:

* أنها ضرورية فعلاً.
* أنها مستقرة.
* أنها مدعومة.
* أنها لا تضيف تعقيداً غير ضروري.

---

# مراجعة الكود قبل الرفع

قبل رفع أي تحديث إلى GitHub.

يجب مراجعة:

* الأخطاء البرمجية.
* صلاحيات الصفحات.
* Validation.
* Logs.
* المسارات.
* الجلسات.
* قاعدة البيانات.

---

# قائمة التحقق النهائية

قبل اعتماد أي تطوير جديد:

* [ ] تم إنشاء الجدول المطلوب.
* [ ] تم إنشاء Class جديد.
* [ ] تم إنشاء صفحات Module.
* [ ] تم إضافة Validation.
* [ ] تم إضافة Permissions.
* [ ] تم إضافة Logs.
* [ ] تم اختبار الميزة.
* [ ] تم تحديث Documentation.
* [ ] تم رفع التحديث إلى GitHub.

---

# فلسفة التطوير في Hodoor

أي تطوير جديد يجب أن يحافظ على:

* بساطة المشروع.
* وضوح الكود.
* سهولة الصيانة.
* سهولة التوسع.
* توحيد أسلوب البرمجة.

الهدف ليس إضافة أكبر عدد من الميزات، بل بناء نظام مستقر ومنظم يمكن تطويره لسنوات دون الحاجة إلى إعادة هيكلته من جديد.
